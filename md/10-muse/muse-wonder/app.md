# Muse Wonder · 앱

## 1. 분야 규칙 — 앱 (모바일)

iOS·Android 앱과 Flutter·React Native 같은 크로스플랫폼 앱에 적용한다. 데스크톱 프로그램은 `native` 문서를 따른다.

### 1.1 구현 규칙
- **플랫폼 규약을 먼저 본다.** 해당 플랫폼의 최신 SDK·가이드라인·심사 정책을 공식 문서로 확인하고, 빌드 도구 버전(Xcode, Android Gradle Plugin, Kotlin·Swift)은 프로젝트 설정을 바꾸기 전에 현재 값을 읽는다.
- **권한은 최소로, 필요한 순간에 요청한다.** 거부·부분 허용·나중에 철회된 경우의 화면을 반드시 만든다. 위치·사진·연락처·알림 권한은 사용 목적 문구와 일치해야 한다.
- **수명주기를 전제로 한다.** 백그라운드 전환, 프로세스 종료 후 복원, 회전·폰트 크기·다크 모드, 네트워크 끊김, 저전력 모드에서 상태가 깨지지 않게 한다. 메인 스레드에서 I/O·무거운 연산을 하지 않는다.
- **비밀은 앱 안에 두지 않는다.** API 키·서명 키·토큰을 바이너리·리소스에 넣지 않는다. 사용자 토큰은 Keychain·Keystore에 저장하고, 서버가 권한을 최종 판단한다.
- **개인정보 선언과 실제 동작을 일치시킨다.** 수집 항목, SDK가 수집하는 데이터, 개인정보 처리방침·데이터 안전 양식이 서로 맞는지 사람이 확인한다. 서드파티 SDK는 라이선스와 수집 데이터를 확인한 뒤에만 넣는다.
- **접근성.** VoiceOver·TalkBack 이름과 순서, 최소 터치 영역, 동적 글꼴, 색에만 의존하지 않는 표시를 확인한다.
- **기존 UI 체계를 따른다.** 프로젝트의 디자인 토큰·컴포넌트·내비게이션 구조를 유지하고, 플랫폼 기본 동작(뒤로가기, 제스처)을 깨지 않는다.
- **네이티브 라이브러리는 16KB 메모리 페이지 정렬을 확인한다.** (아래 표 참고)
- **번역 문구는 사람이 검수한다.** 출시 전에 원어민이 읽고, 용어집으로 일관성을 점검한다.

### 1.2 시점에 민감한 사실
아래 표는 확정된 사실이 아니라 작업 전에 공식 출처로 다시 확인할 출발점이다. 근거로 인용할 때는 직접 확인한 출처와 날짜를 함께 쓰고, 출처마다 다르다고 적힌 항목은 한쪽으로 단정하지 않는다.

| 항목 | 내용 |
|---|---|
| Apple 빌드 요건 | 2026-04-28부터 Xcode 26 이상, iOS 26 SDK로 빌드해 업로드. 2027-04부터 Xcode 27·iOS 27 SDK, 타깃 iOS 15 이상으로 올라간다고 안내됨 |
| Apple 연령 등급 | 4+, 9+에 13+·16+·18+ 추가. 2026-11-16부터 신규 설명자(공유 위치, 데이팅·관계), 선언 기한 2027-01-12 |
| Google Play 타깃 API | 신규 앱·업데이트는 API 36(Android 16) 이상. 기한 2026-08-31이 지났고 연장 신청 안내가 있었음. 기존 앱 유지 기준은 API 35 |
| Android 개발자 인증 | 2026-09-30 브라질·인도네시아·싱가포르·태국에서 집행 시작, 2027년 전 세계 확대 계획. 인증 앱 등록 필요 |
| 16KB 페이지 | Android 15 이상을 타깃하는 앱은 16KB 페이지 지원 필요(2025-11-01 적용, 연장 있었음). 이후 추가 연장설은 단일 글이라 Play Console 확인 |

### 1.3 검증 (작은 것부터)
1. 컴파일·린트 → 2. 변경한 로직의 단위 테스트 → 3. 시뮬레이터·에뮬레이터에서 해당 화면 실행 → 4. 권한 거부·오프라인·화면 회전 경로 → 5. 가능하면 실기기 → 6. 릴리즈 빌드(난독화·서명 포함) 마지막.
시뮬레이터에서만 확인했으면 "실기기 미확인"이라고 보고한다. 심사 통과나 스토어 정책 준수를 단정하지 않는다.

### 1.4 하지 않는다
- 서명 키·키스토어·프로비저닝 프로파일을 읽거나 출력하거나 커밋하지 않는다. 배포·스토어 제출은 사용자 승인 후에만 한다.
- 사용자 동의 없이 데이터를 수집·전송하는 코드를 넣지 않는다. 목적과 맞지 않는 권한을 추가하지 않는다.
- 플랫폼이 금지한 우회(비공개 API, 동적 코드 다운로드 실행, 정책 회피용 난독화)를 쓰지 않는다.

## 2. 이 모델에서 지킬 점 — 앱
- **기기 안에서 돌릴 모델이 아니다.** 폐쇄형이며 가중치를 받을 수 없다. 앱은 서버를 거쳐 호출하는 구조만 가능하다. 모바일 온디바이스는 `gemma-4-e2b`, `gemma-4-e4b` 문서를 본다.
- **API 키를 앱 바이너리나 리소스에 넣지 않는다.** 앱에서 직접 호출하지 말고 자체 백엔드에서 키 보관, 사용량 제한, 요청 검증, 로깅을 한다. 모델 출력은 신뢰하지 않는 입력으로 취급해 서버에서 검증한 뒤 앱에 전달한다.
- **Active Memory를 앱 기능으로 쓰기 전에 보관 조건을 확인한다.** 대화를 넘어 맥락을 유지하는 기능이라 사용자 정보가 모델 측 서비스에 장기 보관될 수 있다. 앱의 개인정보 선언(Apple 개인정보 영양 표시, Google Play 데이터 보안 양식)과 처리방침, 삭제 요청(정보주체 권리) 처리에 반영할 수 있는지 확인되기 전에는 기억 기능을 켜지 않는다. 제3자(연락처 등)에 대한 개인정보를 기억에 넣지 않는다.
- **개인정보 선언과 실제 동작을 맞춘다.** 사용자 입력을 Meta Model API로 보내면 수집·전송 항목을 선언에 반영한다. 데이터 처리 서술이 충돌하고(학습 불사용 전언 대 약관상 사용 데이터로 API 개선 가능), 보관 기간·영 보관 등급이 공개돼 있지 않다. 출시 전에 약관을 원문으로 읽고, 아동·민감정보는 확인 전에 보내지 않는다.
- **비용을 과제당으로 서버에서 제한한다.** 사용자당 한도, `max_tokens`, 요청 빈도 제한을 서버에 두고 실제 청구서로 확인한다.
- **Wonder Full을 앱 백엔드로 가정하지 않는다.** 공개 API는 Wonder만 제공하고 Full은 Muse Code 구독자 전용이다.
- **모델 교체를 앱 업데이트 없이 할 수 있게 설계한다.** Muse 계열은 석 달 사이에 여러 번 갱신됐다. 서버 쪽 모델 설정, 폴백 모델, 회귀 시험, 기능 플래그를 둔다.
- **안전 분류기의 거부를 UX에 반영한다.** 정당한 요청이 거부될 수 있으므로 거부 응답 처리와 폴백을 설계하고 거부율을 우리 시나리오로 시험한다.
- **코드를 읽고 설명·추적하는 일에 쓴다.** 코드 설명 항목이 최고 수준이고 저장소 변경은 중간이다.
