## 1. 분야 규칙 — 펌웨어

MCU·SoC 펌웨어, RTOS·베어메탈, 부트로더, 드라이버, OTA 업데이트, 임베디드 리눅스 BSP에 적용한다. 보드·회로는 `hardware` 문서를 함께 따른다.

### 1.1 구현 규칙
- **레지스터·타이밍은 문서로 확인한다.** 레지스터 맵, 클럭 트리, 인터럽트 우선순위, 메모리 맵은 데이터시트·레퍼런스 매뉴얼의 개정판에서 읽고 근거 위치는 변경 설명에 남기고 주석에는 두지 않는다. 기억으로 비트 필드를 쓰지 않는다.
- **자원을 정적으로 다룬다.** 힙 할당은 초기화 이후 쓰지 않는 것을 기본으로 하고, 스택 사용량·ISR 중첩 깊이·RAM/Flash 예산을 맵 파일과 도구로 확인한다. 재귀와 가변 길이 배열을 피한다.
- **ISR은 짧게.** ISR에서 블로킹 호출, 동적 할당, 긴 루프를 하지 않는다. ISR과 공유하는 변수는 `volatile`만으로 충분한지(원자성, 메모리 배리어)를 따져 보고, 필요한 보호를 명시한다.
- **코딩 표준을 따른다.** C는 MISRA C와 CERT C 계열, C++는 MISRA C++ 계열을 프로젝트 기준에 맞춰 적용하고, 정적 분석 경고는 억제하지 않고 고친다. 새 구성요소는 Rust 등 메모리 안전 언어를 검토한다.
- **죽지 않게, 되돌릴 수 있게.** 워치독, 브라운아웃·리셋 원인 기록, 플래시 쓰기 중 전원 차단에 안전한 저장 구조(이중화, 커밋 표식), 쓰기 횟수(마모) 예산을 설계한다.
- **부트와 업데이트는 서명으로 보호한다.** 이미지 서명 검증, 롤백 방지 카운터, 실패 시 이전 이미지로 복귀, 업데이트 중 전원 차단 복구를 갖춘다. 서명 키는 저장소에 두지 않는다. 양산 장비는 디버그 포트(JTAG·SWD)와 부트 모드를 잠근다.
- **취약점 대응 체계를 갖춘다.** 구성요소 목록(SBOM)과 서드파티 라이선스, 취약점 접수·패치·고지 절차를 유지한다.
- **암호.** 검증된 라이브러리의 상수 시간 구현을 쓰고, 난수는 하드웨어 TRNG 등 검증된 원천을 쓴다. 장기 운용 제품의 서명 방식은 양자내성 전환 일정(아래 표)을 고려한다.
- **프로그래머와 시리얼 제어 도구는 읽기 전용부터 연결한다.** 쓰기 명령은 도구의 권한과 훅으로 막고, 사람이 대상 장치와 이미지를 확인한 뒤에만 연다.

### 1.2 시점에 민감한 사실
아래 표는 확정된 사실이 아니라 작업 전에 공식 출처로 다시 확인할 출발점이다. 근거로 인용할 때는 직접 확인한 출처와 날짜를 함께 쓰고, 출처마다 다르다고 적힌 항목은 한쪽으로 단정하지 않는다.

### 1.3 검증 (작은 것부터)
1. 컴파일 경고 0 → 2. 정적 분석 → 3. 호스트에서 돌리는 단위 테스트(하드웨어 추상화 뒤쪽 로직) → 4. 시뮬레이터·에뮬레이터 → 5. 실제 보드(HIL)에서 해당 기능 → 6. 전원 차단·업데이트 실패·워치독 경로 시험.
실제 보드에서 실행하지 못했으면 "하드웨어 미검증"이라고 보고한다. 컴파일 성공을 동작 확인이라고 말하지 않는다.

### 1.4 하지 않는다
- 플래시 소거·퓨즈/OTP 쓰기·부트로더 덮어쓰기·보호 비트 설정은 되돌릴 수 없다. 사용자의 명시적 승인과 대상 장치 확인 없이 실행하지 않는다.
- 서명 키, 디버그 인증 정보, 양산 이미지를 읽거나 출력하거나 커밋하지 않는다.
- 데이터시트와 맞지 않는 "일단 돌아가는" 레지스터 값이나 지연(`delay`)으로 타이밍 문제를 덮지 않는다.
- 안전 관련 기능(모터, 가열, 배터리, 의료)을 승인된 절차 없이 완료로 선언하지 않는다.

## 2. 이 모델에서 지킬 점 — 펌웨어
- **"끝까지 하라"는 지침을 쓰면 정지점을 명시한다.** 그 밖의 단계에는 정지점을 넣지 않는다.
- **상태를 바꾸는 명령 전에 근거를 확인하게 한다.** 같은 블록은 "시스템 상태를 바꾸는 명령(재시작, 삭제, 설정 변경) 전에 증거가 그 행동을 실제로 뒷받침하는지 확인하라, 알려진 고장과 비슷해 보이는 신호가 다른 원인일 수 있다"고 말한다. 브링업에서 "리셋 원인이 워치독 같다"는 추측으로 설정을 바꾸지 않고, 로그·레지스터 값을 먼저 확인한다.
- **긴 HIL 실행 중 침묵을 막는다.** 보드에 쓰는 단계 직전에 한 줄 의도 설명을 요구하고, 직렬 로그처럼 UI가 숨기는 도구 출력은 "사용자는 이 출력을 보지 못한다. 필요한 내용은 답변에 적어라"라고 알린다.
- **보조 스크립트는 남기지 않는다.** 일회성 확인용 스크립트는 실행 후 지우고, 영구 테스트는 저장소 관례에 맞는 것만 남긴다. 플래시·소거 스크립트는 실행 전에 읽는다.
- **긴 세션 요약에는 정확한 값을 남긴다.** 레지스터 값, 주소, 클럭 설정, 핀 번호, 시험 절차는 요약에서 의역하지 않는다.
- **"통과했다"는 모델의 판단을 쓰지 않는다.**
- **보고의 진술이 Opus 5.5보다 오해를 부른다.** 가장 어려운 세션에서 오해를 부르는 진술이 4배 넘게 나왔다. 완료·원인 진술은 로그와 diff로 대조한다.
- **코딩 기본 모델은 Opus 5.5로 두고 Fable은 어려운 한 문제에만 올린다.** 비용이 약 1.5배인데 결과는 더 낫지 않았다.
