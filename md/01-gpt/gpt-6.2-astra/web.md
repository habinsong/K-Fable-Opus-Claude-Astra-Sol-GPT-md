## 1. 분야 규칙 — 웹

웹 프런트엔드, 백엔드 API, 풀스택 웹 서비스에 적용한다.

### 1.1 구현 규칙
- **입력은 믿지 않는다.** 서버에서 검증하고, 출력은 컨텍스트별(HTML·속성·URL·SQL)로 인코딩하며, DB 접근은 파라미터화 쿼리를 쓴다. 클라이언트 검증은 사용성용이지 보안용이 아니다.
- **인가는 서버에서 요청마다, 객체 단위로 검사한다.** 접근 제어 실패가 OWASP Top 10:2025의 맨 위 항목이다. 숨긴 버튼은 인가가 아니다.
- **예외 상황에서는 닫힌 쪽으로 실패한다.** 오류 응답에 스택·쿼리·내부 경로를 담지 않는다. 타임아웃·부분 실패·재시도 경로도 설계한다.
- **공급망을 본다.** 락파일을 유지하고, 새 패키지는 이름 오타·유지 상태·라이선스·설치 스크립트를 확인한 뒤 추가한다.
- **비밀은 서버 환경에만 둔다.** 클라이언트 번들, 로그, URL 쿼리에 넣지 않는다. 쿠키는 `HttpOnly`·`Secure`·`SameSite`를 기본으로 하고, CSP·HSTS·`X-Content-Type-Options`·`Referrer-Policy`를 점검한다.
- **접근성은 기능이다.** 시맨틱 HTML, 키보드만으로 모든 조작, 보이는 포커스, 텍스트 대비 4.5:1 이상, 폼 레이블과 오류 안내, 이미지 대체 텍스트. 목표는 WCAG 2.2 AA다.
- **성능 예산을 지킨다.** 75퍼센타일 기준 LCP 2.5초 이하, INP 200ms 이하, CLS 0.1 이하를 목표로 하고, 이미지 크기·지연 로딩·번들 크기를 먼저 본다.
- **기존 UI 체계를 따른다.** 사용 중인 프레임워크, 컴포넌트, 디자인 토큰, Tailwind 같은 유틸리티를 쓰고 새 디자인 시스템을 들이지 않는다. 인라인 스타일은 프로젝트가 이미 쓸 때만 쓴다.
- **상태를 빠뜨리지 않는다.** 로딩·빈 상태·오류·비활성 상태를 유지한다. 프로토타입 요청이 아니면 동작하는 척하는 가짜 상호작용을 만들지 않는다.
- **한국어 UI 문구는 짧고 구체적으로.** 마케팅 문구를 쓰지 않는다. 날짜·통화·정렬은 로케일(`ko-KR`)을 따르고, 개인정보는 최소 수집·목적 고지 원칙을 지킨다.

### 1.2 시점에 민감한 사실
아래 표는 확정된 사실이 아니라 작업 전에 공식 출처로 다시 확인할 출발점이다. 근거로 인용할 때는 직접 확인한 출처와 날짜를 함께 쓰고, 출처마다 다르다고 적힌 항목은 한쪽으로 단정하지 않는다.

| 항목 | 내용 |
|---|---|
| WCAG | 2.2가 현행 권고이며 ISO/IEC 40500:2025로 채택(2025-10). 3.0은 2026-03 워킹 드래프트라 법적 기준이 아님 |
| 유럽 접근성법(EAA) | 2025-06-28 적용. 기술 기준은 EN 301 549(WCAG 2.1 AA 수준) |
| 미국 ADA Title II | WCAG 2.1 AA 요구. 시한이 출처마다 다름(2026-04-24 / 2027-04-26 연장설) → 법무 확인 |
| OWASP Top 10:2025 | A01 접근 제어 실패, A02 보안 설정 오류, A03 소프트웨어 공급망 실패(신규), A10 예외 상황 처리 실패(신규) |
| Core Web Vitals | LCP ≤2.5s, INP ≤200ms, CLS ≤0.1 (p75). 변경 시 사전 고지 정책 |

### 1.3 검증 (작은 것부터)
1. 타입체크·린트 → 2. 변경한 로직의 단위 테스트 → 3. 실제 브라우저에서 해당 화면 확인(콘솔 오류, 실패한 네트워크 요청) → 4. 키보드 탭 순서와 스크린리더 이름 확인 → 5. 도구가 있으면 접근성·성능 점검 → 6. 마지막에 빌드.
브라우저에서 확인하지 못했으면 "화면 미확인"이라고 보고한다. 타입체크 통과를 "동작 확인"으로 말하지 않는다.

### 1.4 하지 않는다
- 인가를 클라이언트 검사만으로 처리하지 않는다. 비신뢰 입력을 `innerHTML`·`eval`에 넣지 않는다. 자격 증명이 있는 요청에 CORS `*`를 쓰지 않는다.
- 서드파티 스크립트·폰트·트래커를 라이선스·개인정보·무결성(SRI) 확인 없이 추가하지 않는다.
- 접근성·보안 규정을 "충족했다"고 단정하지 않는다. 확인한 항목과 하지 못한 항목을 나눠 보고한다.

## 2. 이 모델에서 지킬 점 — 웹
- **UI 품질에 대한 평가가 갈린다.** 반면 여러 개발자 후기는 UI 완성도(여백, 타이포그래피, 마감)가 Fable 5.1보다 약하다고 보고한다. → 라우팅·상태 관리·API 연동·테스트는 Astra에 맡기고, 시각 완성도는 스크린샷을 직접 대조해서 확인한다. 디자인 비중이 큰 화면은 같은 요구사항으로 Fable 5.1과 한 번 비교해 본다.
- **과잉 설계를 막는다.** 새 컴포넌트·유틸·스크립트를 만들기 전에 프로젝트에 이미 있는 것을 먼저 찾는다. 변경 후 `git diff --stat`으로 새로 생긴 파일이 요청에 필요한 것인지 확인한다.
- **완료 기준을 시작할 때 적는다.** 예: "해당 화면이 브라우저에서 열리고, 콘솔 오류가 없고, 키보드만으로 조작되며, 관련 테스트가 통과한다." 중간 검토를 위해 멈추라는 지시는 넣지 않는다(일찍 멈추는 쪽으로 기운다).
- **접근성·성능·보안을 "충족했다"는 자기 판단을 증거로 쓰지 않는다.** 접근성 도구, 브라우저 콘솔, 성능 측정 출력으로 확인한다.
- **시각 확인.** 스크린샷은 모델의 해석이 아니라 실제 렌더링과 대조한다.
- **며칠씩 도는 자율 작업을 맡기지 않는다.** 컴파일러 이식에서 진척이 없고 오히려 느려진 사례와 사소한 질문에서 두 시간 뒤 멈춘 사례가 보고됐다.
- **간단한 버그에 경계 사례 조사와 방어 코드를 덧붙인다.** 변경 범위를 요청에 묶는다.
- **코드베이스에 없는 사실을 말하는 일이 보고됐다.** 파일이 열려 있어도 그렇다. 코드 설명은 원문과 대조한다.
- **완료를 일찍 선언한다.** 요구사항 목록을 항목별로 대조한다.
- **보고서가 장황하고 저수준에 치우친다.** 상위 요약부터 쓰게 한다.
- **요청을 문자 그대로 받아 모호한 점을 되묻는 편이다.** 의도와 완료 기준을 적는다.
- **구독 한도를 빨리 소진한다는 증언이 있다.** 긴 작업 전에 남은 한도를 확인한다.
