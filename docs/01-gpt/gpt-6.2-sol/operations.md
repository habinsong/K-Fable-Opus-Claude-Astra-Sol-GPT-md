#### 2.2 API를 쓸 때
- **도구 호출은 Responses API로 한다.** 두 모델 모두 Chat Completions를 지원하지만 도구 호출에는 Responses가 필요하다고 가이드가 적는다. [확인]
- `temperature`, `top_p`, `top_logprobs`를 보내지 않고, Responses의 `include`에서 `message.output_text.logprobs`를 뺀다. Chat Completions에서는 `logprobs`도 뺀다. effort `none`은 API가 거부한다. 옛 코드의 `none`·`minimal`은 `low`로 바꿔 비교한다. [확인]
- **대화 중 모델을 바꾸거나 앞선 입력을 고치지 않는다.** 6.2부터 Responses API는 중간 편집, 모델 변경(다운그레이드 포함), 최종 사용자·조직 변경이 있으면 reasoning 항목을 버린다. 답변 품질이 떨어지고 토큰 사용이 늘 수 있다고 가이드가 경고한다. 이력은 append-only로 둔다. [확인]
- 최상위 `instructions`는 `input` 뒤에 붙는다. 캐시되는 지침은 `developer` 메시지로 `input`의 첫 항목에 둔다. GPT-5.5 이하에서 옮길 때는 `prompt_cache_retention`을 `prompt_cache_options.ttl`(`"30m"`)로 바꾼다. [확인]
- ZDR은 승인된 조직의 적격 엔드포인트에서 지원된다. `store`가 `false`로 취급되므로 이전 출력 항목을 암호화된 reasoning 항목까지 순서대로 돌려준다. [확인]
- 데이터 레지던시: Standard·Fast·Batch는 US·EU, Ultrafast는 US만 지원한다고 가이드가 적는다. GPT-6.1 Sol 문서에는 Fast가 EU에서 불가라고 적혀 있다. 변경으로 읽되 계약 전에 가격·레지던시 페이지로 다시 확인한다. [확인/부분]
- 모델 문자열만 바꾸지 말고 같은 effort로 기존 모델과 먼저 비교한다.

#### 2.3 행동 특성과 지침 문서를 쓰는 법
- 가이드의 프롬프트 권고는 이 저장소 §0·§1과 같은 방향이다. 합리적이고 되돌릴 수 있는 가정으로 진행하고, 범위 변경·차단·사용자 결정·되돌릴 수 없는 동작에서만 멈추게 한다. 끝에는 요청과 대조하는 검증을 시키고, 코딩에서는 프로젝트 관례·재사용 기대·테스트가 필요한 때를 적는다. [확인]
- 가이드는 Astra가 기본 출력이 더 간결하고 직접적이라고 적는다. 6.1 이하에서 쓰던 "간결하게" 지침은 다시 검토한다. [확인]
- 같은 규칙을 반복해서 적지 않는다. 충돌하는 지침 파일이 있으면 사용자 지시가 우선한다고 한 번만 적는다.
- 최종 보고는 5항목, 항목당 1~2줄로 쓴다.
- 6.1 Sol 때 OpenAI는 구체적인 절차·제약·검증 명령을 적어 주는 것이 Sol에 더 도움이 된다고 언급했다. 6.2 Sol에도 그대로라는 근거는 없다. 시작 때 통과해야 할 검증 명령을 직접 적는 방식은 유지하되 효과는 직접 비교한다. [추정]
